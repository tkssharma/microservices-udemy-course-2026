📜 Event Sourcing

Store Events, Not State — With Real-World Examples

🎯 What is Event Sourcing?

💡 Core Concept

📜 Definition

Instead of storing current state, store all events that led to that state. The current state is derived by replaying events. Every change is an immutable event in an append-only log.

❌ Traditional (CRUD)

Account Balance: $500

Only stores current value. History lost. Can't answer "how did we get here?"

✅ Event Sourcing

• AccountCreated: $0
• MoneyDeposited: +$1000
• MoneyWithdrawn: -$500

Full history. Can replay anytime.

📦 Components

📝 Commands

Intentions to change state: CreateAccount, DepositMoney, WithdrawMoney

📜 Events

Facts that happened: AccountCreated, MoneyDeposited, MoneyWithdrawn

💾 Event Store

Append-only database storing all events. Source of truth.

📊 Projections

Read models built from events. Optimized for queries.

✅ Benefits

🎯 Why Event Sourcing?
  • 📜 Complete Audit Trail: Every change is recorded. Perfect for compliance.
  • ⏪ Time Travel: Reconstruct state at any point in time.
  • 🔍 Debugging: Replay events to understand bugs.
  • 📊 Multiple Projections: Build different read models from same events.
  • 🔄 Event Replay: Fix bugs, rebuild projections, migrate data.
  • 📈 Analytics: Historical data enables powerful analytics.

⚠️ Challenges

🚧 Things to Consider

📈 Event Schema Evolution

Events are immutable. How to handle schema changes? Use upcasters.

💾 Storage Growth

Events accumulate forever. Consider snapshots for performance.

🧠 Complexity

Steeper learning curve. Not suitable for simple CRUD apps.

⏱️ Eventual Consistency

Projections may lag behind. Design for eventual consistency.
