📊 CQRS Pattern

Command Query Responsibility Segregation

🎯 What is CQRS?

💡 Core Concept

📖 Definition

CQRS separates read and write operations into different models. Commands (writes) modify state. Queries (reads) return data. Each can be optimized independently.

✏️ Command (Write)

  • 📝 CreateOrder
  • 📝 UpdateProduct
  • 📝 CancelOrder
  • 💾 Write Database

🔍 Query (Read)

  • 📖 GetOrderDetails
  • 📖 ListProducts
  • 📖 GetUserOrders
  • 💾 Read Database

🏗️ The Pattern

🔄 CQRS Flow
Command
→
Write Model
→
Event
→
Read Model
📦 Components

📝 Commands

Intent to change state. CreateOrder, UpdateInventory. Validated before processing.

🔍 Queries

Request for data. Read-only. No side effects. Optimized for specific views.

💾 Write Store

Normalized database. Optimized for writes. Source of truth.

📊 Read Store

Denormalized views. Optimized for queries. Can use different database.

🛒 E-Commerce Example

📦 Order System with CQRS

✏️ Write Side

  • PlaceOrder → Validate stock, create order
  • PayOrder → Process payment
  • ShipOrder → Update shipping status
  • 💾 PostgreSQL (normalized)

🔍 Read Side

  • OrderDetails → Full order with items, shipping
  • OrderHistory → User's past orders
  • OrderDashboard → Analytics view
  • 💾 Elasticsearch (denormalized)

✅ Benefits

🎯 Why CQRS?
  • 📈 Independent Scaling: Scale reads and writes separately
  • ⚡ Optimized Queries: Denormalized views for fast reads
  • 🔧 Flexibility: Different databases for read/write
  • 📊 Simpler Models: Focused, single-purpose models
  • 🔄 Event Sourcing Friendly: Natural fit with event-driven systems

🤔 When to Use?

📋 Good Fit

✅ Use CQRS When

• Read/write patterns differ significantly
• Complex queries needed
• High read/write ratio
• Scaling requirements differ

❌ Avoid CQRS When

• Simple CRUD operations
• Small applications
• Team unfamiliar with pattern
• Strong consistency required
