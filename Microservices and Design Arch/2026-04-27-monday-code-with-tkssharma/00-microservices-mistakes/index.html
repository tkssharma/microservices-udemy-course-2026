⚡ Challenge #1: Service Dependencies

❌ The Problem: Cascading Failure
📦
Order Service
Waiting...
💳
Payment Service
30s timeout...
🏦
Bank API
💀 DOWN
1

Bank API is slow (30s timeout)

External service having issues

2

Payment Service threads blocked

Waiting for Bank API response

3

Order Service threads blocked

Waiting for Payment Service

4

💀 ENTIRE SYSTEM DEAD

One slow service killed everything

✅ The Solution: Circuit Breaker Pattern
✅
CLOSED
Normal operation
→
🚫
OPEN
Failures exceed threshold
→
🔄
HALF-OPEN
Test if recovered

✅ CLOSED State

Requests flow through normally. Circuit monitors for failures.

🚫 OPEN State

After 3 failures, circuit OPENS. Returns fast failure immediately. No waiting!

🔄 HALF-OPEN State

After 30s, allows one test request. Success → CLOSED. Failure → OPEN again.

💻 Code Example
// Circuit Breaker with NestJS
@Injectable()
export class PaymentService {
  private circuitBreaker = new CircuitBreaker({
    failureThreshold: 3,    // Open after 3 failures
    resetTimeout: 30000,    // Try again after 30s
  });

  async processPayment(data) {
    return this.circuitBreaker.execute(() => {
      return this.callBankAPI(data);
    });
  }
}

📤 Challenge #2: Reliable Messaging

❌ The Problem: Dual-Write Failure
1

✅ Save order to Database

await db.save(order) - Success!

💥

APP CRASHES HERE

Server restarts, pod killed, exception thrown...

2

❌ Publish event to RabbitMQ

await rabbitMQ.publish(event) - NEVER EXECUTED!

💀 Result

Order exists in DB, but Payment Service never gets notified. Customer charged? Maybe. Maybe not. DATA INCONSISTENCY!

✅ The Solution: Transactional Outbox Pattern
📦 Orders Table
order_id: "abc-123"
status: "pending"
amount: $99.99
+
📤 Outbox Table
event_type: "order.created"
payload: {...}
published: false

☝️ BOTH saved in SAME database transaction - Atomic!

1

Single Transaction

Save order + outbox event in ONE atomic transaction

2

Background Worker Polls

Every 5s, find events where published = false

3

Publish to RabbitMQ

Send event, then mark published = true

4

Crash Safe!

If app crashes, event stays in outbox. Worker picks it up later.

🔑 Challenge #3: Duplicate Messages

❌ The Problem: Double Processing
1

Payment Service processes payment ✅

Customer charged $99.99

2

Try to ACK the message

Sending acknowledgment to RabbitMQ...

3

💥 Network blip - ACK fails!

Connection dropped before ACK received

4

RabbitMQ thinks message wasn't processed

No ACK received, must be unprocessed...

5

RabbitMQ re-delivers message

Payment processed AGAIN! 💀

6

Customer charged TWICE! 😱

$99.99 + $99.99 = Angry customer + Refund + Bad reviews

✅ The Solution: Idempotency Keys
📨
Message
ID: abc-123
🔍
Check Redis
processed:abc-123?
✅
Process Once
Skip if exists

🔑 How It Works

Every message has a unique ID. Before processing, check Redis if this ID was already processed. If yes, skip it.

⏰ TTL for Cleanup

Store processed IDs with TTL (e.g., 24 hours). Old entries auto-expire to prevent memory bloat.

📜 The Rule

Design EVERY message handler to be idempotent. Assume messages WILL be duplicated.

❌ The Problem: Where Did It Fail?
[Order Service] [INFO] Processing order abc-123
[Payment Service] [ERROR] Something went wrong
[Notification] [INFO] Waiting for events...
[Inventory] [DEBUG] Stock check complete
[Order Service] [INFO] Order complete???

Which service failed? WHY? No idea. 🤷
✅ The Solution: Distributed Tracing with OpenTelemetry
Trace ID: abc-123-def-456
├── Order Service (200ms)
├── Validate order (10ms) ✅
└── Call Payment Service (150ms)
└── Payment Service (140ms)
├── Check balance (20ms) ✅
├── Process payment (50ms) ✅
└── Call Bank API (60ms) ❌ TIMEOUT
└── Total: 200ms - FAILED at Bank API call

🔗 One Trace ID

Single ID follows request across ALL services. Complete request journey visibility.

📊 Spans & Timing

See exactly how long each step took. Identify bottlenecks instantly.

🎯 Pinpoint Errors

Know exactly WHERE and WHY it failed. No more log hunting!

🛠️ Tools

Jaeger, Zipkin, AWS X-Ray, Datadog - all work with OpenTelemetry

⏱️ Challenge #5: Latency Management

❌ The Problem: Timeout Chain Disaster
API Gateway
30s
└ Order Service
30s
└ Payment Service
30s
└ Bank API
30s

💀 Result

User waits 30 seconds... then gets error. All resources held for 30 seconds... then released. Terrible UX!

✅ The Solution: Timeout Budgets
API Gateway
10s (total budget)
└ Order Service
8s
└ Payment Service
5s
└ Bank API
3s

⚡ Fail FAST

Inner services timeout first. Fail quickly, release resources, let caller decide next step.

🔄 Room for Retries

Outer timeout > inner timeout + retries. Otherwise you retry after caller gave up!

📉 Budget Propagation

Pass remaining budget downstream. Services know how much time they have.

💻 Code Example
// Proper timeout + retry strategy
const axiosInstance = axios.create({
  timeout: 3000, // 3 second timeout
});

async function callExternalAPI(data) {
  return retry(
    () => axiosInstance.post('/api', data),
    {
      retries: 3,
      minTimeout: 1000,
      maxTimeout: 3000,
    }
  );
}
